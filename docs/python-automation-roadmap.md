# Python 自动接管路线图

这份文档回答 3 个问题:

1. 现在到底有没有标准流程记录
2. 什么时候能把“独立 py 自动接管脚本”做出来
3. 先做哪些平台最合适

## 当前结论

有记录，而且不只是一份零散笔记。

当前已经落下来的标准操作基线有:

- [`browser-operation-sop.md`](./browser-operation-sop.md)
- [`browser-tab-takeover-runbook.md`](./browser-tab-takeover-runbook.md)
- [`latest-success-flow.md`](./latest-success-flow.md)
- `workflow/content-library/examples/`

所以现在不是“从零整理规则”。

真正还没完成的是:

- 把这些规则编码成每个平台一套稳定的 Python 执行器
- 把 selector / frame / 风控检查点恢复逻辑固化下来

## 什么情况下可以开始做

满足下面 5 个条件，就可以正式开做:

### 1. 浏览器会话策略定下来

建议固定成二选一:

1. `Playwright + connect_over_cdp` 接管已经登录的 Chrome
2. `Playwright persistent context` 使用专用用户目录

如果两种方式混着来，后面最容易乱。

### 2. 输入内容格式定下来

建议不要直接从零散 Markdown 到处抓字段。

先固定一份机器可读包，例如:

- `content-package.yaml`
- 或 `content-package.json`

至少统一这些字段:

- campaign id
- 主标题
- 平台标题
- 正文 / 描述
- 主视频路径
- 3:4 封面
- 4:3 封面
- 话题 / 标签

### 3. 每个平台的真相源定下来

每个平台都要先定义:

- 发布入口
- 管理页入口
- 成功信号
- 停止条件

比如:

- 视频号: `列表页出现新条目` 才算成功
- 抖音: `作品管理` 里 `审核中` 才算成功
- 知乎: 公开页可见才算成功

### 4. 人工检查点策略定下来

下面这些不能假装不存在:

- 短信验证码
- 滑块
- 百度安全验证
- 二次登录
- 风控问答

所以这套 Python 工程的目标，不该定义成“100% 无人值守”。

更现实的目标是:

- 可接管
- 可暂停
- 可恢复
- 可验证
- 可记录

### 5. 验收标准定下来

建议每个平台至少达到这个门槛再算“可用”:

1. 同一平台连续 2 次成功
2. 至少 1 次从旧标签页或半成品页恢复成功
3. 发布后能自动回管理页验证
4. 能正确在检查点暂停并提示人工介入

## 建议的交付顺序

按“稳定性 + 页面复杂度 + 风控强度”排序，建议这样推进:

1. 快手
2. 头条号
3. 微博
4. 百家号
5. 知乎
6. 抖音
7. 微信视频号
8. 小红书

原因:

- 快手 / 头条号更适合先做“管理页校验 + 草稿恢复”
- 视频号最复杂，最好放到后面单独打磨
- 小红书常有界面变化和风控，不建议拿来做第一枪

## 时间预估

在“已有稳定登录态 + 已有 1 组完整发布素材 + 不需要重新摸索入口”的前提下:

- 1 个平台试点版:
  - `0.5 ~ 1` 天
- 3 个平台可复用版:
  - `2 ~ 3` 天
- 8 个平台半自动 v1:
  - `5 ~ 7` 个工作日

如果中间需要重新定位 selector、补风控恢复、重新验证管理页逻辑，周期会继续拉长。
