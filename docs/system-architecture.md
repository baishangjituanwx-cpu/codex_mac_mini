# 系统架构

## 1. 总体分层

这套流程按四层理解最稳:

1. 内容生产层
   - `campaign brief`
   - `production pack`
   - 视频素材
   - 封面素材
2. 发布执行层
   - 浏览器后台发布
   - 各平台单独验证
   - 发布日志回填
3. 协同通知层
   - Feishu bot
   - Codex bridge
   - 任务进度推送
   - 发布成功推送
4. 复盘沉淀层
   - content package
   - publish log
   - review skill
   - 次日优化清单

## 2. 关键组件

### A. 飞书桥接

位置:

- `skills/codex-feishu-bridge-skill/`

职责:

- 把飞书私聊绑定到本地 Codex thread
- 支持 `/new` `/resume` `/threads` `/history`
- 推送任务进度
- 监控发布线程，自动推送发布完成摘要

实现:

- Node
- `@larksuite/cli`
- 本地 `codex` CLI
- `launchd` 后台服务

### B. 内容库

位置:

- `workflow/content-library/`

职责:

- 保存每次 campaign 的主包和分平台包
- 保存发布日志
- 保存二次优化结果
- 作为复盘输入源

### C. 浏览器执行

当前状态:

- 不是固定 Python 仓库脚本
- 是 Codex 驱动浏览器自动化会话
- 每个平台按本地验证过的 SOP 执行

为什么这样整理:

- 平台后台经常变
- 真正稳定的是“页面验证信号”和“人工检查点处理规则”
- 所以要沉淀 SOP、字段映射、验证标准，而不是伪稳定脚本

### D. 复盘层

位置:

- `skills/multi-platform-content-review-skill/`
- `workflow/content-library/logs/`

职责:

- 区分 `已发布 / 审核中 / 暂缓 / 待登录 / 未执行`
- 判断内容问题、平台问题、账号问题、路由问题
- 输出 `Keep / Cut / Retest`

## 3. 推荐主流程

1. 先定母题和核心判断
2. 产出源视频和封面
3. 写全平台主包
4. 写分平台包
5. 开后台逐个平台发
6. 每个平台验证后立即飞书推送
7. 回填日志
8. 做 batch review
9. 生成次日优化清单

## 4. 为什么发布成功推送要逐平台发

不是整批结束再推，而是每个平台验证完成就推一次。

原因:

- 平台结果到达时间不同
- 有的平台是 `已发布`
- 有的平台是 `审核中`
- 有的平台会卡登录、验证、去重
- 逐平台推送更适合真实运营节奏

## 5. 这套仓库里最重要的三个事实

1. 当前浏览器侧成功路径，核心不是“某个脚本”，而是“先有标准内容包，再按 SOP 验证”
2. 飞书桥接已经代码化且可迁移
3. 复盘的结构化沉淀已经足够支持下一轮自动化
